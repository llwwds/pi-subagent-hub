`bin/pihub` 只查找已构建的 Rust 二进制，找不到时打印构建指令并失败，不会


显式指定。需要本机已有 Rust 工具链时，可设置

运行（开发/试用）：

普通 CLI 从环境变量解析 hub home；若当前 shell 继承了在用的 `PIHUB_HOME`，
照抄下面的命令会直接操作那个实例（包括在用的 2.0）。所以开发/试用请显式指定一个
明确的私有 home，不要依赖继承值：

```bash
export CARGO_TARGET_DIR="${CARGO_TARGET_DIR:-${TMPDIR:-/tmp}/pihub-rust-target}"
export PIHUB_HOME="$(mktemp -d /tmp/pihub-dev-home.XXXXXX)"

./bin/pihub --version        # 3.0.0.0
./bin/pihub config init --json
./bin/pihub daemon start --json
./bin/pihub daemon status --json
./bin/pihub daemon stop --json
```

要跑真实 end-to-end（daemon + panel）的开发环境，更推荐只用已核验的 QA helper，
它强制显式 canonical 私有 home 并做 receipt + daemon.json + health + 真实进程
身份核验，start/status/stop 都不吃 ambient `PIHUB_HOME`：

```bash

    --binary "${CARGO_TARGET_DIR}/release/pihub" --receipt /tmp/pihub-dev-qa.json

    --receipt /tmp/pihub-dev-qa.json
scripts/qa-instance.sh stop   --home /tmp/pihub-rust-qa-<name>/hub \
    --receipt /tmp/pihub-dev-qa.json --cleanup
```

正式安装后的 CLI 契约不变：`pihub` 仍按 `PIHUB_HOME`（缺省时用默认 home）工作，
本次没有修改 launcher 对 `PIHUB_HOME` 的任何行为；变化只在文档示例，避免把开发
命令指向在用的部署。

### Launcher 的 app root

`bin/pihub` 是唯一知道真实仓库根位置的组件。显式设置了 `PIHUB_APP_ROOT` 时一律
尊重；未设置时**无条件**把它设为仓库根再启动二进制。这样 `CARGO_TARGET_DIR` 指向
`/tmp/...` 的外置构建不会让二进制从 `<target>/release` 猜测 appRoot，`config paths`、
`doctor`（`pi-lock`/`pi-commit`/`pi-cli`）与 `vendor/pi` 都指向真实部署根。
appRoot 不依赖 `vendor/` 是否已下载：缺 vendor 时在正确根报告真实缺项，而不是
回退到二进制父目录。launcher 从不设置或修改 `PIHUB_HOME`，不猜 cwd，也不硬编码
任何设备路径。部署布局仍是 `<app_root>/bin/pihub`。

普通 CLI（含 config/doctor/daemon 启停）只使用 `LocalOps` 和 loopback HTTP；
只有隐藏的 `__daemon` 分支构造 `HubStore`/`AgentManager`/`RuntimeFactory`。
daemon 是 SQLite 与事件流的唯一写入者。

## 2.1 线上契约（本轮对齐）

公开 agent 视图恢复 2.1 `publicAgent()` 的投影：`/v1` 与 `/v2` 都带
`tools`、`skills`、`extensions`，且仍不暴露任何 `*_json` 原始列。冻结了 skill
授权的 Agent，`skills[]` 就是授权对象 `{id,path,sha256}`（2.1 没有独立 `grants`
字段，授权只通过 `skills`、`skillIds`、`skillPolicy.ids` 呈现）。

事件行同时返回 `payload`（解析后的对象）和 `payload_json`（数据库中保存的原始
文本，逐字节一致）。`/v2/carriers` 与 CLI carrier 列表的 `reason` 在可用时
序列化为 `null`，不再省略键。

`/v2/agents/:id/stop|restart` 与 dashboard 的 abort/stop/restart 用存在性门禁，
响应仍是 2.1 的 legacy 形状；`/v1` 路由保留 legacy-only 门禁（平台 Agent 返回
`agent_not_found`）。这一条是候选构建内的真实修复：此前的实现在 v2/dashboard
复用了 `/v1` 视图门禁，导致平台 Agent 的停止/重启/中止返回 404。

错误包封以 2.1 为准：域错误（CC Switch 不支持、carrier 不可用、prompt 配置无效）
在 wire 上统一为 `400 request_failed` 并**保留原始 message**，仅
`agent_not_found` 保留自身 code。`doctor` 的第一项恢复为 `node`（Pi 仍是 Node
bundle），daemon 检查恢复 2.1 的扁平 health 形状。

### 已接受的可观察差异

`session_file` 从 2.1 的共享 `<TARGET_WORK>/user-home/session.jsonl` 变为每 Agent
私有的 `<HOME>/agents/<uuid>/state/pi-home/session.jsonl`。这是隔离改进带来的
**有意的**公开字段变化，已作为已知差异接受，不在归一化里静默抹平。

**同轮事件落库顺序**（显式接受，不归入 harness 噪声）：在同一个 turn 内，2.1 记
`agent_start` 在前、`command_accepted` 在后；3.0 因为 runtime 事件经有界 channel
交给异步 pump 落库，内联的 `command_accepted` 先于 pump 里的 `agent_start`。这是
**同一 Agent 流内唯一**的顺序差异。

`agent_settled` 没有延后：按真实 `agent_id` 直接读各自 `hub.sqlite` 核对，两侧的
`agent_settled` 都落在**该 Agent 自己**的 `message_end` 之后（legacy cursor 11、
platform cursor 12），每轮一次、settled 后进入 idle hold。合并列表里看起来像
“两条 settled 都排在第 2 轮之后”，那只是归一化把 `<UUID>` 折叠后两个 Agent 交错的
观感，不是每 Agent 的 settle 被推迟。

两侧代码都是“await runtime.request(...) 之后再记 command_accepted”（
`core/src/manager.rs:707-737` 对 `src/manager.js:532-537`）；顺序差异来自通路：
2.1 用同步 `EventEmitter`，Rust 用有界 channel + pump。事件**多集、每 Agent 计数、
因果不变量（一轮一个 accepted、start<message_end、settled 在末尾）完全一致，无丢失**，
差异只在 accepted/start 的先后与 cursor 落点。

要精确复刻 2.1 的顺序，必须在 request 返回后对同一 Agent 做一次 drain/fence 等待
pump 排空；这会与已定的“不为时序匹配加 drain/fence”相悖，并用 CONC-1 的隔离/身份
保证和延迟去换顺序。因此**由集成者显式接受为已知差异并记录在此**，不做静默归一化。

## 内存对照（有限边界，非普适性能保证）

独立内存代理在**冻结候选** `2299ad2e...` 上的对照（`/tmp/pihub-rust-memory.json`，
phase=complete）：

| Hub daemon resident RSS | Node 2.1 | Rust 3.0 |
| --- | --- | --- |
| steady，0 agents | 37.09 MiB | 4.48 MiB |
| steady，1 agent | 37.17 MiB | 4.97 MiB |
| steady，4 agents | 43.90 MiB | 5.05 MiB |
| 采样窗口内最大值，0 / 1 / 4 | 38.64 / 48.72 / 50.86 MiB | 4.48 / 7.05 / 7.23 MiB |

| 短命 CLI max RSS | Node 2.1 | Rust 3.0 |
| --- | --- | --- |
| `--help` | 50.58 MiB | 4.41 MiB |
| `config paths --json` | 50.47 MiB | 4.80 MiB |
| `daemon status --json` | 50.39 MiB | 4.97 MiB |

steady 比值 Rust/Node 约 0.115～0.134，采样最大值比值约 0.116～0.145。

方法：同一私有 fake-Pi home，0/1/4 agents，12 次有界 run（0 与 4 重复 n=2～3，
1 为 n=1），100 ms 采样、4000 ms 窗口，取窗口尾部中位数作为 steady；采样最大值是
**采样窗口内观测到的最大值**，不是真实瞬时峰值的上界（100 ms 间隔看不到更短的
瞬时尖峰）。CLI 用 macOS `/usr/bin/time -l` 的 maximum resident set size，
每条命令重复 3 次。

边界：Node 仍是 macOS arm64 的 v26.0.0，换 Node 大版本会改变其基线；**该轮 Node
列有噪声**：4 agents 时出现 37.2 → 50.7 MiB 的跨度（当时 parity full9 同时在跑），
Rust 列稳定（0 agents 多次重复一致，4 agents 差异在 3% 内），因此 Node 列应作为
锚点而不是精确基线，单次差值不能当作跨负载/跨平台的普适结论。载体子进程是
fake-Pi Node fixture，单独统计、两侧对等、**不计入** Hub 收益；本次只测 resident
RSS，未测 private footprint/共享页/swap，也不是整集群或长期峰值数据。

## 有界运行时事件通道

Rust carrier 事件进入 core 的单个有界 channel（容量 1024）。独立 probe 在早期
候选 `231a4b7b...` 上得到：

| 场景 | 实测 |
| --- | --- |
| 正常消费 200 events | `get_state` 1ms；200 全部送达、保序、无丢失 |
| 暂停消费后请求 | `get_state` 命中声明超时 15s；恢复消费后 drain 5.1s，200 保序、0 重复、`agent_settled` 可见 |
| 满队列时 stop | 7.2s 完成；无孤儿进程 |

这是有意接受的有界背压取舍：暂停消费时后续 response 可能命中声明超时，恢复后
仍保序不重复；stop 仍能终止进程树。它不是“永不 starve/满队列不会阻塞响应”的
保证，也没有额外无界队列或第二通道。

注意：上表是在早期候选 `231a4b7b...` 上测的，内存对照已改在冻结候选上重测，
但 channel probe 尚未重跑；在重跑完成前，不要把这三行当作最终 hash 上的结论。
